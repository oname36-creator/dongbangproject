# 4주 개발 계획 — 비상하는 강철의 환상

기획서(`동방프로젝트_기획서.md`) 11장의 4주 일정을 **현재 코드베이스의 실제 상태에 맞춰** 구체화한 실행 계획이다.

---

## 0. 이 문서를 쓰는 법

- 각 주차는 `목표 → 작업 → 완료 기준 → 함정` 순으로 되어 있다. **함정 항목을 먼저 읽어라.** 대부분 실제 코드를 확인하고 뽑은 것이라 모르고 진입하면 반나절씩 날아간다.
- 날짜 단위로 잘게 쪼개지 않았다. 주 단위 목표와 **순서(의존성)** 만 지키면 된다. 순서를 지키지 않으면 뒤 작업이 막힌다.
- 매주 끝에는 **반드시 실행되는 빌드**가 남아야 한다. "이번 주는 리팩터링만 하고 다음 주에 돌아가게 만들겠다"는 계획은 4주 프로젝트에서 가장 위험하다.

---

## 1. 시작 시점의 현황: 기획서와 실제 코드의 격차

기획서는 *"이미 구현된 Unity풍 기반 구조(SceneManager, Component, Map 등)를 활용한다는 전제"* 로 작성되었다. **이 전제는 현재 절반만 맞다.** 실제 상태는 다음과 같다.

### 이미 있는 것 (그대로 활용)

| 시스템 | 위치 | 비고 |
|---|---|---|
| Actor + Component 구조 | `Engine/Actor.h`, `Engine/Component.h` | `AddComponent<T>()` / `GetComponent<T>()` 동작함 |
| 스프라이트 렌더링 | `Engine/ImageRenderer`, `Engine/SpriteRenderer` | 시트 분할(row/col), 애니메이션, 투명색 지원 |
| 원형 충돌 + 그리드 | `Engine/ColliderCircle`, `Engine/CollisionManager` | Enter/Stay/Exit 3단계, `ActorType` 쌍별 무시 마스크 |
| 오브젝트 풀 | `Engine/ObjectPool.h` | Bullet/Enemy에 적용됨 |
| 델타타임 + **콜백 타이머** | `Engine/TimeManager.h` | `AddTimer(func, interval, loop)` — **웨이브/보스 패턴 스케줄링에 그대로 쓸 수 있다** |
| 입력 | `Engine/InputManager.h` | Down/Press/Up 3상태 구분됨 |
| JSON 데이터 로딩 | `Engine/DataManager`, `Client/ResourceData` | 텍스처 정의를 JSON에서 읽음 |
| 렌더 레이어 정렬 | `Client/Scene.cpp` `_renderList` | `RenderLayer` enum 순서대로 그림 |

### 없는 것 (이번 4주에 만들어야 함)

| 기획서 요구 | 현재 상태 | 최초 필요 시점 |
|---|---|---|
| **SceneManager, 씬 전환** | `Game`이 `Scene` 1개를 `new`로 직접 소유. `Scene`에 virtual 없음 | **1주차** |
| GameScene 상태머신(Ready→Playing→Boss→Clear) | 없음 | 1주차 |
| **게임 에셋 전체** | `Resources/` 완전히 비어 있음 (bmp 0개, JSON 0개) | **1주차 Day 0** |
| 잔기 / 폭탄 / 무적시간 | Player는 `_hp = 100`, 피격당 -10 뿐 | 1주차 |
| 저속 이동 | 없음. `KeyType`에 Shift 자체가 없음 | 1주차 |
| 탄막 패턴(부채꼴/원형/나선/조준) | `Bullet`은 `_dir` 고정 직선만 | **2주차** |
| 보스 / 페이즈 / 체력바 | 전혀 없음 | 2주차 |
| 점수 | 없음 (`Enemy::OnEnter`에 `// 점수 증가` 주석만 있음) | 2주차 |
| 스테이지 / 웨이브 정의 | `createRandomEnemy()`를 2초마다 반복하는 게 전부 | 2주차 |
| 적 체력 | **없음. 적은 무조건 1히트 사망** | 2주차 |
| 사운드 | 전혀 없음 (라이브러리 링크조차 안 됨) | 2주차 |
| 패럴랙스 배경 | `WorldBG`는 큰 이미지 1장 + 카메라 스크롤. 레이어 없음 | 2주차 |
| 아이템 / 드롭 / 파워업 | `Client/Bullet.h`에 `Item` 클래스가 빈 껍데기로 선언만 됨 | 3주차 |

### 기획서 용어 ↔ 실제 코드 이름

기획서를 보며 작업할 때 이름이 달라 헤매지 않도록:

| 기획서 | 실제 코드 |
|---|---|
| `Vector2` | `Vector` (`Common/Util.h`) |
| `TransformComponent` | 없음 — 위치는 `Actor::GetPos()/SetPos()`에 인라인 |
| `SpriteRendererComponent` | `ImageRenderer`(정지) / `SpriteAnimRenderer`(애니메이션) |
| `ColliderComponent` | `ColliderCircle` (원형만 있음, 사각형 없음) |
| `HealthComponent` / `MovementComponent` / `WeaponComponent` | 없음 — 각 클래스 안에 인라인 |
| `Map` / `StageDirector` | 없음 — `Scene`이 배경·스폰을 직접 들고 있음 |
| `GameObject` | `Actor` |

## 2. 4주를 관통하는 3가지 원칙

### 원칙 1 — 기획서 4장의 컴포넌트를 전부 만들지 마라 ★

기획서 4장은 `TransformComponent`, `HealthComponent`, `MovementComponent`, `WeaponComponent`, `DropComponent` 등 9종 컴포넌트를 제시한다. **이걸 전부 도입하는 건 이번 4주에서 하지 마라.**

이유: 현재 `Player`/`Enemy`/`Bullet`은 컴포넌트 조합이 아니라 **상속 + 인라인 로직**으로 짜여 있고, 그게 이미 동작한다. 이걸 컴포넌트로 쪼개는 건 순수 리팩터링이라 **플레이 가능한 결과물이 1도 늘지 않으면서** 기존에 돌던 충돌/풀/타이머를 전부 다시 검증해야 한다. 한 달짜리 프로젝트에서 가장 흔한 실패 원인이다.

**만들 가치가 있는 컴포넌트는 딱 2개다:**
- `BulletPattern` — 여러 적/보스가 같은 발사 패턴을 공유하므로 실익이 크다 (2주차)
- `BossPhase` — 페이즈 순환 로직이 보스마다 반복되므로 실익이 크다 (2주차)

나머지(체력, 이동, 무기)는 **각 클래스의 멤버 변수로 그냥 둬라.** 적 체력은 `Enemy`에 `int32 _hp;` 한 줄이면 끝난다.

### 원칙 2 — 매주 금요일에 "남에게 보여줄 수 있는 빌드"가 있어야 한다

주차 목표를 못 채우면 **기능을 줄여서라도 실행되는 상태로 주를 마감**한다. 반쯤 뜯어놓은 상태로 주말을 넘기면 월요일에 복구하는 데만 하루가 든다.

### 원칙 3 — 막히면 12장의 Could부터 버린다

기획서 12장 우선순위를 그대로 따른다. 일정이 밀릴 때 **Must(3스테이지·보스·충돌)를 지키기 위해 Should(파워업·중간보스·스코어 저장)를 먼저 버린다.** 판단을 미루지 말고 각 주차 마지막 날에 결정한다.

## 3. 1주차 — 플레이 기반 완성

> **목표:** 타이틀에서 시작해 적을 쏘고, 피하고, 죽고, 재시작까지 되는 1분짜리 루프.

### Day 0 (반나절) — 블로커 해제 ★ 여기부터 시작

**이걸 안 하면 나머지 전부가 눈으로 확인이 안 된다.** 최우선.

1. **리소스 경로 고정.** `Client/Game.cpp`의 `Game::Init()`은 현재 `GetCurrentDirectory() / "../Resources/"` 를 쓴다. 프로젝트 파일이 레포 루트에 있으므로 비주얼 스튜디오로 실행하면 이 경로가 **레포 바깥**을 가리킨다. 경로를 `Resources/`로 바꾸고 디버깅 작업 디렉터리를 `$(ProjectDir)`로 맞추는 게 가장 단순하다.
2. **플레이스홀더 에셋 제작.** 그림 실력은 지금 중요하지 않다. **단색 사각형/삼각형이라도 좋으니** 다음을 `Resources/`에 채운다: `Player.bmp`, `Enemy1~4.bmp`, `PlayerBullet.bmp`, `EnemyBullet.bmp`, `explosion.bmp`, `PlayerHP.bmp`, `World_BG.bmp`. 투명색은 기존 코드 관례대로 마젠타 `RGB(255,0,255)` 계열을 쓴다.
3. **`Resources/Data/ResourceData.json` 작성.** 스키마는 `Client/ResourceData.cpp`의 `Load()` 참고. 이 JSON에 없는 텍스처는 로드되지 않는다(`Scene::loadResources()`가 JSON만 읽는다).

> **확인:** 실행했을 때 배경·플레이어·적·총알이 화면에 보이면 Day 0 완료.

### Day 1~2 — 씬 구조 세우기

기획서 3장의 4개 씬(Title/Game/Result/Ending)을 담으려면 씬 추상화가 먼저다. **이건 나중으로 미룰수록 비싸진다.** `Scene`에 코드가 쌓인 뒤에 쪼개려면 훨씬 아프다.

- `Scene`을 추상 베이스로 전환: `virtual ~Scene()`, `virtual Init/Cleanup/Update/Render`
- 현재 `Client/Scene`의 내용을 `GameScene`으로 옮기고, 베이스 `Scene`은 얇게 유지
- `TitleScene`, `ResultScene`을 **껍데기로** 추가 (배경 + 안내 문구 + 키 입력 하나). 화려하게 만들지 마라
- `Engine/SceneManager` 싱글톤 추가. `Game`은 씬을 직접 소유하지 말고 위임

### Day 3~4 — 플레이어 사양을 기획서 5장에 맞추기

- **`KeyType`에 키 추가** (`Engine/InputManager.h`): 현재 enum에 **Shift·Z·X가 아예 없다.** 저속이동/폭탄/발사키를 쓰려면 먼저 추가해야 한다
- 저속 이동: Shift 입력 시 이동 속도 40~50%
- 자동 연사: 현재 `GetButtonDown(SpaceBar)`이라 **누를 때 1발만** 나간다. 발사 쿨다운을 두고 `GetButtonPressed`로 전환
- **잔기/폭탄 체계로 교체:** 현재 `Player`는 `_hp = 100`에 피격당 `-10`이다. STG 표준대로 **피격 1회 = 잔기 -1**, 초기 잔기 3 / 폭탄 2 / 피격 후 무적 1.5~2초로 바꾼다
- **히트박스 축소** (기획서 4장): 현재 콜라이더 반지름은 스프라이트 크기(`renderer->GetSizeX()`)에서 온다. 플레이어만 **반지름 4~6px 고정**으로 줄인다. 탄막 게임의 체감을 좌우하는 핵심이다
- 폭탄: 화면 내 적 탄환 전부 제거 + 짧은 플래시

### Day 5 — 탄환/풀 정리 (2주차 탄막의 전제조건) ★

**2주차에 원형탄·부채꼴탄을 넣기 전에 반드시 끝내야 한다.** 안 하면 2주차 첫날에 게임이 터진다.

- **화면 밖 판정에 x축 추가:** `Client/Bullet.cpp`는 지금 `y`만 검사한다(`y < 0 || y > GWinSizeY`). 직선탄만 있을 땐 문제없지만, **좌우로 퍼지는 탄이 생기는 순간 화면 밖으로 나간 탄이 영원히 안 죽고 풀을 잠식한다**
- **풀 크기 상향:** `GameScene`의 `_bulletPool.Init(100)`은 원형탄 한 번(20발)에 순식간에 고갈된다. **1000 이상**으로 올린다
- **고갈 시 방어:** `ObjectPool::Acquire()`는 고갈되면 `assert` 후 `nullptr`을 반환하는데, `CreateBullet()`은 반환값을 검사하지 않고 바로 `bullet->Init()`을 호출한다 → **널 역참조 크래시**. null 체크를 넣는다
- **좌표계 정리:** 현재 `Scene`은 "화면보다 큰 월드 + 플레이어를 따라가는 카메라" 구조인데, 종스크롤 STG는 화면 고정 + 배경만 스크롤하는 쪽이 훨씬 단순하고 기획서 7장(패럴랙스)과도 맞는다. **카메라 코드를 지우지 말고 `_cameraPos`를 화면 중앙에 고정**하면 월드 좌표 = 화면 좌표가 되어 안전하게 단순화된다

### Day 6~7 — 상태머신 · HUD · 첫 웨이브

- `GameScene` 상태머신: `Ready → Playing → Boss → Clear / GameOver` (enum + switch로 충분하다)
- HUD: 잔기·폭탄·점수. **이미지 만들지 말고 `TextOut`으로 시작해라.** 폴리싱은 4주차에 한다
- 일시정지, 게임 오버 → ResultScene 이동
- Stage 1 웨이브 프로토타입: `createRandomEnemy()`의 랜덤 스폰을 **`{시간, 적 종류, 위치}` 배열**로 교체 (기획서 5장 원칙대로 외부 데이터화하지 말고 코드 테이블로)

> **완료 기준:** 타이틀 → 게임 → 피격 → 게임오버 → 결과 → 타이틀이 끊김 없이 순환한다. 적을 쏘고 피하는 1분 분량 플레이가 가능하다.

**이번 주 주로 만지는 곳:** `Client/Scene→GameScene`, `Client/Player`, `Client/Bullet`, `Engine/InputManager.h`, `Engine/SceneManager`(신규), `Resources/`

## 4. 2주차 — 전투 콘텐츠 확장

> **목표:** Stage 1을 처음부터 보스 격파까지 완주 가능.

> **참고:** 점수 시스템(`GameScene::_score`, `Enemy::OnEnter`의 점수 가산)은 1주차 진행 중 이미 구현됨. 아래 일정에서 제외.

탄환 클래스를 늘리지 말고 **`Bullet` 하나에 속도·방향·스프라이트·이동타입**을 넣어 재사용한다 (기획서 6장 지침). 아래 Day1~2가 그 전제 작업이다.

### Day 1 — 탄막 파이프라인 열기 ★ 여기부터 시작

- **`Bullet::Init()` 시그니처 확장:** 지금은 `BulletType`만 받고 방향을 내부에서 고정한다. **방향(`Vector dir`)과 속도(`float speed`)를 인자로 받도록 바꾼다.** `GameScene::CreateBullet()`도 함께 확장. 이 변경이 이번 주 나머지 전부의 전제다
- 기획서 6장 발사 함수 5종 중 우선 2종: `FireStraight` / `FireAimed`
- 기존 호출부(`Player::fire`, `Enemy::shootBullet`)를 `FireStraight`로 교체해서 회귀 확인

> **확인:** 플레이어/적이 기존과 동일하게 총알을 쏘되, 내부적으로는 방향 인자를 받는 구조로 바뀌어 있으면 Day1 완료.

### Day 2 — 패턴 3종 추가

- 나머지 발사 함수 구현: `FireFan`(부채꼴) / `FireCircle`(원형) / `FireSpiral`(나선)
- 함정: 원형탄 한 번에 20발이 나가므로 풀(1000) 고갈 여부 재확인, 화면 밖 판정(x축 포함)이 실제로 다 정리하는지 확인

> **확인:** 적 한 종류에 임시로 붙여서 부채꼴/원형/나선 3패턴이 화면에서 육안으로 확인되면 Day2 완료.

### Day 3 — 적 콘텐츠 확장

- **적 체력 도입:** 현재 적은 무조건 1히트에 죽는다. `Enemy`에 `int32 _hp` 추가 (컴포넌트로 만들지 말 것 — 원칙 1)
- 적 종류를 4종으로 늘리고 각 적에 Day1~2에서 만든 패턴 중 하나씩 배정
- **함정:** `Enemy`는 `Init()`에서 `TimeManager::AddTimer`로 발사 타이머를 걸고 `Destroy()`에서 해제한다. **풀에서 재사용될 때 타이머가 중복 등록되거나 유령 타이머가 남기 쉽다.** 적 종류가 늘어나는 이번 날 반드시 확인할 것 (이미 죽은 적이 계속 쏘는 버그로 나타남)

> **확인:** 4종의 적이 각자 다른 패턴으로 쏘고, 체력만큼 맞아야 죽으면 Day3 완료.

### Day 4 — 보스 뼈대

- `Boss` 클래스 + `BossPhase` 구조체 작성 (기획서 8장)
- **`ActorType`과 `RenderLayer`에 `Boss` 추가** (`Common/Util.h`) — 충돌 무시 마스크 배열 크기가 `ActorType::Count` 기반이라 enum만 늘리면 자동 반영된다
- 페이즈 전환 로직: 기존 탄 삭제 → 짧은 무적/연출 → 다음 패턴

> **확인:** 보스가 등장해서 페이즈 전환이 최소 2단계까지 넘어가면 Day4 완료 (탄막 내용은 아직 placeholder여도 됨).

### Day 5 — 보스 완성 + 클리어 연결

- Stage 1 보스 3페이즈 각각에 Day1~2 패턴을 배정해서 실제 탄막 채우기
- 보스 체력바 + 이름/패턴명 표시
- `GameScene` 상태머신의 `Boss → Clear` 전환을 실제 보스 격파 이벤트에 연결

> **확인:** Stage 1을 시작부터 보스 3페이즈 격파 → Clear까지 끊김 없이 진행되면 Day5 완료.

### Day 6 — 배경/사운드 + 전체 점검

- Stage 2 배경 + 일반 웨이브
- 패럴랙스: 배경을 최소 2레이어로. 같은 텍스처 반복으로 아트 부담을 줄인다 (기획서 7장)
- **사운드 최소 적용:** `PlaySound()` 또는 `mciSendString`. `Common/pch.h`에 `#pragma comment(lib, "winmm.lib")` 추가 필요. 발사·폭발·피격 3종이면 체감이 확 산다
- 2주차 완료 체크리스트(8절) 4항목 전체 재확인

> **완료 기준:** Stage 1을 시작부터 보스 격파까지 완주할 수 있다. 효과음이 최소 3종 재생된다.

## 5. 3주차 — 3스테이지 제작

> **목표:** 3개 스테이지를 처음부터 끝까지 진행 가능.

- 유도탄, 격자/교차탄 추가 (기획서 6장 중간 난이도 패턴)
- **Stage 2 보스** + 유도탄/공간 제한 기믹
- **Stage 3** 맵 · 웨이브 · 중간보스
- **최종 보스 4페이즈** + 엔딩 연출
- 파워업 3단계 (Should — 일정 빠듯하면 여기서 버린다)
- **디버그 키 정비 (이번 주 생산성을 좌우한다. 먼저 해라):**
  - `KeyType`에 `F1`, `F2`, `KEY_1`, `KEY_2`가 **이미 정의되어 있다.** 바로 쓸 수 있다
  - `CollisionManager`에 `_drawDebug` 플래그가 **이미 있다** → F2에 연결하면 충돌 원이 보인다
  - F1 = 무적 토글, 숫자키 = 스테이지 즉시 이동. 이게 없으면 3스테이지 테스트에 매번 15분씩 쓴다

> **완료 기준:** Stage 1 → 2 → 3 → 엔딩까지 이어서 진행할 수 있다.

**주의:** 이번 주가 물리적으로 가장 빡세다. 3주차 중반에 진도가 절반 미만이면 **Stage 3의 중간보스를 버리고 일반 웨이브 강화 구간으로 대체**한다 (기획서 3장이 허용하는 대체안).

---

## 6. 4주차 — 폴리싱 및 안정화

> **목표:** 재시작 없이 전체 게임을 완주할 수 있는 빌드.

- **주 초반에 Release 빌드 확인 ★** — PCH 설정이 `Debug|x64` 구성에만 걸려 있다. Release 구성은 지금까지 한 번도 빌드해본 적이 없으므로 **제출 직전이 아니라 주 초반에 확인한다**
- 난이도·탄속 조정. 조정 대상 상수를 **한 파일에 모아두면** 반복 튜닝이 빨라진다
- 기획서 13장 테스트 체크리스트 9항목 전부 통과
- 누수/중복 점검: 씬 재전환 시 적·탄환·점수·UI 중복, 타이머 잔존, 풀 미반환
- UI 가독성, 이펙트, 사운드 보완 (1주차에 `TextOut`으로 뒀던 HUD를 여기서 다듬는다)
- **최소 3회 이상 전 구간 플레이 테스트** — 본인 말고 다른 사람에게 시켜보면 난이도 감각이 교정된다
- 마지막 이틀은 **버퍼로 비워둔다.** 반드시 뭔가 터진다

> **완료 기준:** 일반적인 플레이로 처음부터 끝까지 완주 가능한 빌드 확보.

## 7. 일정이 밀릴 때 버리는 순서

위에서부터 버린다. **아래 3개는 끝까지 지킨다.**

1. 엔딩 연출 → 텍스트 한 장으로 대체
2. 파워업 3단계
3. 중간보스 → 일반 웨이브 강화로 대체
4. Stage 3 고유 기믹
5. 스코어 저장 / 난이도 선택
6. 사운드를 효과음 3종으로 축소
7. Stage 3을 짧게 (7분 → 4분)
--- 여기부터는 버리지 않는다 ---
- 3스테이지 각각의 보스
- 충돌 판정의 정확성과 화면 밖 정리
- 게임오버 / 클리어 / 재시작

## 9. 최종 판단 기준 (기획서 14장 재확인)

> 시작 → 적과 탄막의 규칙 학습 → 보스 공략 → 클리어 보상 → 다음 스테이지 도전

이 흐름이 **끊기지 않는 것**이 성공 기준이다. 아트와 기능의 양보다 **조작감, 충돌 정확도, 탄막의 가독성, 보스전의 완주 가능성**을 우선한다.
